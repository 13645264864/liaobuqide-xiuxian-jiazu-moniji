# 真人家族文字修仙：首版技术与界面方案

状态：设计草案，已同步初始 2 个名额、后续需父母同意和跨家族二选一规则。本文不代表已实现或已部署。

依据：同目录 `requirements.md`。已确认交付 Android 安装包和电脑网页端，共用账号进度；前 50 名有创世待遇，成婚自动生成 2 个无需父母审批的子女名额，后续新增子女需父母同意。跨家族子女可以选择父母任一家族。

## 1. 首版可玩的范围

先实现一个完整循环：入世 → 认识家庭和家族 → 闭关 → 祭拜/扩容 → 突破试炼 → 收集资源 → 参与小兽潮 → 成婚与传承/分家。

游戏世界中已有地点、交通和黑云山背景，但首版主要开放一个州内的若干地点、一种小兽潮和一套基础资源。其余区域展示明确的未开放状态，不使用假的成功提示。全面家族战争、海岛经济和黑云山反攻在后续阶段接入同一架构。

必须同时验证真人互动与客户端交付：多个真实账号确实形成家庭关系，Android APK 可安装，电脑浏览器能读取同一角色。

## 2. 客户端与后台选择

| 层级 | 建议技术 | 原因 |
| --- | --- | --- |
| 共同界面 | React + TypeScript + Vite | 文字界面与表单、聊天适配容易，网页直接运行 |
| 样式与图标 | Tailwind CSS + Lucide | 统一尺寸与字体，少量线条图标即可 |
| Android | Capacitor，内置网页构建产物 | 复用界面，同时生成独立安装包；不依赖每次在线下载页面才能启动 |
| 登录 | CloudBase Auth | 账号跨客户端一致，管理登录与游戏用户登录分开 |
| 数据 | CloudBase PostgreSQL | 亲缘、婚姻、资产和名额关系适合关系表与事务 |
| 游戏操作 | PostgreSQL RPC + 必要的后台任务 | 原子处理名额、资源与进度，客户端只提交行动意图 |
| 事件驱动 | 后台定时任务与时间戳结算 | 离线也发生兽潮，不依赖玩家手机常驻后台 |
| 头像 | 首版内置头像，后续开放上传 | 先完成玩法，上传后续再接入 pgstore 与权限 |

客户端读写优先使用 CloudBase Web SDK v3 的 `app.rdb()` 与 RPC，认证用 `auth.getSession()`。Android 内是 WebView 网页上下文；如 SDK 在该来源存在兼容问题，应先验证并修正来源/授权设置，不直接把管理凭证放入 APK。

登录方式实现前查询实际 provider 和 SDK 支持，不能假设用户名注册接口存在。用户名密码登录可作为首版方向，具体注册以已验证的 CloudBase 支持为准。

建议使用独立 CloudBase PostgreSQL 环境，账号、包名、资源与数据均与其他游戏隔离；不能复用其他游戏角色表。

新游戏正式源码应放到独立项目目录；当前文档暂存在现有仓库，不代表未来把新游戏塞进 Godot 工程。独立目录的创建权限与实际位置仍需落实。

## 3. 界面设计规格

### 用途与风格

让玩家随时知道「我是谁的孩子、属于哪个家族、现在该修炼还是回去支援」，并能在手机上用少量操作完成挂机收益、亲缘互动和守城行动。

采用古籍与族谱的编辑式布局：浅纸色底、墨色文字、横向细线、世代编号、家族印记与连续事件记录。信息以文字行和小型状态栏组织，不以大量装饰卡片或全屏场景图片为主。

### 色彩、字体与动作

- 纸色 `#F3EBDD`：主背景。
- 墨色 `#252B29`：正文与主要标题。
- 青黛 `#31594F`：修炼、灵气与当前状态。
- 朱砂 `#A74635`：危机、失败与关键警报。
- 旧金 `#9A743E`：品级、族长与宗祠。
- 标题使用 Noto Serif SC，正文使用 Noto Sans SC；构建时打包许可允许的中文字体资源并控制体积，不依赖海外字体服务。
- 图标统一使用 Lucide，配中文文字，不用 emoji 代替功能图标。
- 头像战斗用 CSS/Canvas 的短距离移动与碰撞反馈，日志始终可读；关闭动画时仍能完整理解胜负。

### 布局与四个主要页面

| 页面 | 玩家看到的信息 | 主要动作 |
| --- | --- | --- |
| 修行 | 角色、境界/品级、寿命/道基、灵气当前值与上限、离线报告 | 闭关、领取、扩容、突破、物品 |
| 家族 | 家族简介/威望/领地、宗祠、神兵、成员、家庭与族谱 | 祭拜、愿力、婚约、出生招募、分家/治理 |
| 山河 | 地点目录、距离、行程、兽潮、远征公告 | 出行、参与战斗、修补、求援 |
| 更多 | 账号、设置、说明、其他入口 | 切账号、音效/动画、外部入口 |

手机：纵向阅读，底部四项导航，顶部右侧固定聊天入口；族谱使用可展开的世代列表，避免在窄屏硬塞整棵树。危险提示置于顶部状态带，点开直接进入对应战场。

电脑：左侧窄导航与人物摘要，中间主要操作区，右侧家庭动态/战报。聊天从右上角展开为侧栏，也可扩大；页面结构不变，跨端操作一致。

出生选择、道侣邀请、丹药使用和突破结果采用子页面/抽屉，不增加大量顶级页面。金钱或物品消耗展示数量、收款方或获得效果。

聊天暂保留世界、家族、师徒、家庭、私聊五类信息结构。「全屏」原意未确认，设计兼容全服频道和聊天扩大显示，不把两者混为同一功能。师徒可先展示未开放提示，不制造假的关系。

## 4. 入世与家族关系流程

### 创世序号

用户要求按游戏注册顺序发放前 50 名创世资格。建议把「正式进入游戏并首次建立角色」定义为游戏注册完成，在服务端事务内锁定世界序号，分配不可修改的 `registration_order`。CloudBase 认证账号存在但从未入世，不先占用创世资格。这个具体计数边界需用户确认。

首名入世玩家创建原始家族，设置为族长。序号 2～50 可加入原始家族或自建家族；加入者不同时获得原始家族的族长权力。序号 51 起只能领取可用的真人子女名额。

建议每位创世玩家有独立的一对已故先祖，使他们有各自血缘来源，而不会因同在原始家族就被认定为亲兄弟姐妹；此为建议，尚未确认。先祖只有谱系节点，没有可登录身份。

### 结为道侣与名额生成

两名玩家自愿接受同一道侣邀请；验证婚配条件、成婚告知和礼金规则。事务成功时一起写入道侣关系和 2 个候补子女名额。初始两个名额领取无需父母另行批准。

初始两个名额领满后，额外接纳新子女必须取得父母同意，不设置无限自动补充。任一父母同意即可开放额外名额；具体批准数量和失效规则尚待细化；未完成所需同意前，不生成已出生角色或抢占子女关系。

父母分属不同家族时，子女可选择父母任一家族，并检查所选家族的适用接纳条件。一份出生资格提供两个家族选项，不复制成两份可分别领取的名额。每份名额仍只能产生一个真人子女。

### 子女出生

选择页列出家族简介、可用出生资格与提前设置的匹配条件，区分可直接领取的初始名额与需要父母同意的额外接纳。选中后由服务端锁定名额，重新检查家族接纳策略、名额状态与必要同意；成功时原子创建玩家角色、亲缘边、家族成员和通知。待批准时明确显示等待，不伪装成已出生。

出生候选先按家族选择、接纳策略与性别/灵根条件过滤，再按初始名额/已批准额外名额分组。默认两个子女名额未满的家庭排在前面，推荐与随机分配先从这些家庭领取；只有当前选择范围内没有可用初始名额时，才考虑已批准的额外名额。同优先级可采用可配置的公平随机规则，不用「哪个家庭更有钱」改变优先级。

玩家明确选择一个符合条件的家庭时，不因其他家庭有更高推荐优先级而替换其选择。服务端执行自动分配时锁定并重新检查候选；并发导致名额耗尽则在同一选择范围内重新匹配，不能错误越过仍有可用初始名额的家庭。

家族若只禁止随机出生，不能因此错误拒绝主动选择；性别/灵根筛选对两种路径的具体适用范围仍需确定。

当多个用户同时选择最后一个名额时，只能一个成功。已领取者重复点击或网络重试返回第一次出生结果。没有名额时展示候补等待状态，不生成 NPC 父母顶替真人。

### 家庭、家族与独行

谱系边、道侣关系和家族成员关系分别保存。分家变更当前家族，不重写父母；独行是角色状态，不删除成员或亲缘记录。家族名册按当前成员展示，族谱保留历史。

## 5. 数据结构

表名建议统一 `fc_` 前缀，即使使用独立环境也容易识别。以下是逻辑模型，不是已执行的数据库迁移。

| 数据对象 | 关键内容与约束 |
| --- | --- |
| `world_state` | 原始家族 ID、创世序号计数、世界阶段；计数在事务内锁定 |
| `characters` | 唯一 Auth UID（text）、注册序号、性别/灵根、境界、寿命、道基、当前地点与行动 |
| `lineage_nodes` | 真人节点关联角色；虚构先祖无 Auth UID，标记已故；不参与在线人数 |
| `parent_links` | 子女节点与两位父母，角色一生只有一组出生父母；避免祖先循环 |
| `families` | 简介、族长、等级、威望、领地与提前接纳策略 |
| `family_memberships` | 角色当前家族、职位、历史变动；当前家族关系唯一 |
| `marriages` | 双方角色、状态、告知记录；一人只能有一段有效道侣关系 |
| `birth_slots` | 道侣关系、初始/额外类型、可选家族、匹配条件、领取者与状态；单名额单领取者 |
| `birth_consents` | 额外接纳的申请或开放记录、父母意见、批准数量与状态；满足必要同意才允许新增子女 |
| `wallets` / `asset_ledger` | 个人/家族资产余额与原因流水；礼金/赔款事务结算，不允许负余额 |
| `inventory` | 角色物品、数量、装备属性；与资产/战斗结算一起变更 |
| `cultivation_sessions` | 服务端起止时间、闭关地点、收益率版本、结算游标 |
| `buffs` / `breakthrough_attempts` | 宗祠效果、扩容、试炼输入快照、结果与损失 |
| `world_events` / `battle_actions` | 兽潮/试炼状态、参与者选择、动作生效时间 |
| `battle_reports` / `battle_logs` | 输入规则版本、结果与日志；按事件序号分页 |
| `territory_points` | 战略点归属、进度、兵力和最近结算时间 |
| `presence_leases` | 玩家在线租约与过期时间，后台/断网后自动失效 |
| `journeys` | 路线、交通方式、起止时间、抵达状态 |
| `chat_threads` / `chat_messages` | 频道类型、参与权限、消息与阅读游标 |
| `direct_contacts` | 陌生人问候/已回复/屏蔽状态；首次问候唯一约束 |
| `notifications` / `action_receipts` | 出生/危机通知与请求去重结果 |
| `game_rules` | 规则版本及可调数值，活动/战斗记录生效版本 |

关系查询按 ID 和游标批量读，不逐个玩家查询父母或背包。家族列表返回可公开的简介、接纳策略与名额摘要，不返回私人资产和家庭聊天。

## 6. 服务端操作边界

以下是拟定的业务 RPC 名称，实施时通过迁移创建与授权，不是声称 CloudBase 平台自带这些接口。

- 入世：`fc_enter_world`、`fc_claim_birth_slot`。
- 家族：`fc_update_family_profile`、`fc_update_recruitment`、`fc_split_family`。
- 道侣：`fc_propose_marriage`、`fc_accept_marriage`，在确认礼金规则后完成转账及名额生成。
- 额外子女：拟定受控申请/同意操作，服务端校验真实父母、所需同意与批准数量；不允许客户端直接把待批准状态改为已批准。
- 修炼：`fc_start_cultivation`、`fc_settle_cultivation`、`fc_worship_ancestors`、`fc_use_capacity_pill`。
- 试炼：`fc_start_breakthrough`、`fc_resolve_breakthrough`；身份、资源、伤害和结果全部重新核验。
- 战场：`fc_join_battle`、`fc_set_battle_action`、`fc_set_auto_vow`、`fc_request_aid`。
- 旅行：`fc_start_journey`、`fc_settle_journey`。
- 聊天：`fc_send_message`、`fc_send_greeting`、`fc_reply_to_greeting`。

RPC 获取调用者 UID，不信任客户端传入 owner/父母/族长/获胜方。所有改动支持用户与操作类型作用域下的幂等请求 ID；并发操作按固定顺序锁定对象，避免重复领取、重复转账及死锁。

浏览器可直接修改的仅限通过权限约束的普通资料字段；角色属性、亲缘、道侣、出生名额、公共资产、战略点和战斗结果禁止直接更新。

## 7. 挂机、兽潮与头像战斗

修炼收益使用服务器时间计算区间，移动/阵亡/地点变化必须分段结算，不能事后把整段离线时间算成安全家族闭关。扩容只改变容量，实际灵气补充方式在规则确定后实现。

单人试炼首版由服务端基于属性快照和随机结果生成完整战报，客户端按节奏播放头像动作与日志。重新播放日志不再次结算损失或奖励。

兽潮使用有限战略点的行动分配：攻防、修补、供愿。定时任务处理推进与状态转移；客户端打开战场时调用可信结算同步到当前服务器时间，然后读取战况。不能仅靠活跃玩家访问才生成兽潮或触发覆灭。

首版不需要碰撞物理联网，也不逐帧把头像坐标写进数据库。战略点、行动生效时间和结算游标才是持久化状态；头像碰撞由日志生成。

在线愿力必须以服务器记录的心跳租约判断。手机切后台与断网后租约过期，不继续无期限贡献「在线」愿力；Android 在后台无需保持无限运行。自动贡献是玩家选择，由服务端在在线租约和可用资源范围内计算。

严格超过一半战略点丢失进入城墙失守状态；阵亡、求援和旅程抵达采用单次状态转换。跨家族支援受交通抵达时间约束。状态变化通知与日志可在重新进入游戏时补读。

原规则还有待明确的品级挑战方式、五倍兵力含义、复活货币等，实现对应模块前确认，不能把建议值伪装成用户决定。

## 8. 聊天同步与身份权限

先使用按消息序号的短轮询，聊天打开时同步更频繁，关闭或应用进入后台停止轮询；后续可评估平台实时订阅，不能未经验证假设 SDK 已支持 PG 全表订阅。

世界频道登录可读；家族频道需要当前成员关系；家庭频道由确定的家庭关系生成参与者；师徒频道由有效关系授权。使用 RLS 或受控 RPC 验证权限，不只在界面隐藏入口。

未回复陌生人会话里发起方只允许一条问候，回复原子更新会话为正常状态。双方同时首次问候、网络重试、刷新页面都不突破限制。屏蔽会影响消息发送与通知。

默认不提供先祖聊天和虚构在线成员，NPC/系统事件必须标明来源。

## 9. 安全、数据隔离与发布

- Auth UID 按 text 存储；权限用 `auth.uid()`，不使用数据库 `current_user` 当玩家身份。
- 涉及 RPC 提权时固定 `search_path`、检查调用者与对象权限、缩小 EXECUTE 授权；不得让任意玩家以管理权限读写全表。
- 使用版本化 PostgreSQL 迁移，先建资源和权限，再接客户端真实数据。管理密钥不出现在前端、APK 或 Git。
- 首版需要验证 Web 来源与 Android WebView 来源、HTTPS 网络访问及会话持久化，不只验证桌面浏览器。
- APK 使用新包名、新版本记录及独立签名密钥；不能覆盖原游戏签名文件。后续版本保存相同新签名身份。
- 自定义家族文案、消息做长度限制及基本举报/屏蔽；首版先使用内置头像。
- 网页使用 hash 路由，避免子路径刷新依赖托管重写；部署与发布前检查域名、资源路径、隐私说明和账号管理。
- TapTap 链接未提供时传送门展示「链接待配置」，不跳到猜测网址。接入后 Android 用外部浏览器打开。

## 10. 验证与交付证据

| 验证对象 | 通过标准 |
| --- | --- |
| 创世边界 | 并发情况下最多 50 个创世资格，第 51 个走名额；重复请求不再分配序号 |
| 出生关系 | 成婚生成 2 个真实名额，初始领取无需审批；额外子女没有父母同意不能出生；跨家族二选一仍只消耗一份资格；并发领取不重复 |
| 出生优先级 | 列表、推荐与随机分配优先使用默认名额未满且符合条件的家庭；所选范围内初始名额耗尽后才分配已批准额外名额；有效主动选择不被替换 |
| 婚姻与礼金 | 关系、流水与名额同时成功或同时回滚；无资产时按已确定规则处理 |
| 家族隔离 | 别人不能读家庭聊天、修改族长设置或提取家族资产 |
| 修炼与突破 | 服务端时间收益、容量和实际灵气区分；失败损失仅结算一次 |
| 兽潮与城墙 | 无人打开界面也推进；战略点阈值、修补/供愿影响与求援行程真实生效 |
| 私聊 | 第二句未回复问候被服务端拒绝；回复后可连续对话 |
| 跨端 | Android 与电脑登录同一账号看到相同进度，操作不会重复领取 |
| Android 交付 | 构建签名 APK、检查包名/权限，并在可用设备或模拟器安装验证 |
| 网页交付 | 生产构建通过，实际浏览器验证登录/出生/修炼/战斗，记录控制台与布局问题 |

每阶段保留真实运行与后端读回证据。没有 Android 测试设备时，明确区分已生成 APK 与尚未验证安装，不能只凭构建成功宣称手机可玩。
